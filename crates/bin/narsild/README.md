# narsild

`narsild` is a threshold-custody sidecar daemon for Penumbra validators. One
instance runs alongside each participating validator. Together the instances
hold a single threshold key: no node ever materialises the group secret, and no
node can sign alone.

It is a prototype. It is not audited, not wired into `pd`, and not used by any
production system.

## Status

- Self-contained crate: `crates/bin/narsild/Cargo.toml` declares its own
  `[workspace]`, so it is not a member of the Penumbra root workspace and does
  not participate in the workspace lockfile or dependency set. It has its own
  `Cargo.lock` and its own `rust-toolchain.toml` (channel `1.92`, versus the
  repo-wide `1.83`).
- Cryptography comes from the `osst` crate (nested FROST with OSST
  identification, DKG and proactive resharing), on the Pallas curve — the curve
  Zcash Orchard uses for spend authorization. Pinned to **osst 0.4.0**
  (`penumbrafi/frostito` rev `bf30136`) with features
  `std,pallas,sealed`.
- DKG round 2 is sealed and point-to-point; signing is nested FROST **v2** and
  is bound to an epoch and to the roster. Share material is persisted to the
  data directory.
- Resharing, stake weighting and authentication of the HTTP endpoints
  themselves are still not implemented.

> **Keys generated by an earlier `narsild` must be regenerated.** The DKG that
> produced them broadcast plaintext round-2 sub-shares to every peer, so the
> group key is not secret — see *Transport security* below. A key package
> without `"format": 2` is refused at startup with that message.

## Transport security

The threat the daemon has to survive is that one of its own peers is hostile,
because the point of a threshold key is that a minority of the group cannot
use it. Two findings of `osst`'s `SECURITY-REVIEW-2026-09.md` were observed
directly in this crate, and both are fixed here.

### Round 2 is sealed, and reaches one recipient (D-1, D-2)

The previous DKG serialized each round-2 sub-share as a hex scalar and
broadcast the message intended for *every* recipient to *every* peer. A
dealer's polynomial has degree `t-1` and is pinned down by `t` points, so round
2 put `n-1` evaluations of every dealer's polynomial in front of every node:
for any `n > t` — 2-of-3 included — a single participant interpolates the
coefficients and holds the group signing key. That is **D-1 (Critical)**.

Now:

- The wire type for round 2 carries a `osst::sealed` ciphertext and nothing
  else. There is no plaintext sub-share type left in the crate, so no code path
  can emit one, and the round-2 types are `deny_unknown_fields`, so a peer
  still speaking the old protocol is rejected at deserialization rather than
  half-understood.
- Each sealed package is delivered with `PeerSet::send_to` — one recipient, one
  HTTP request. `broadcast` is reserved for data that is public by
  construction (Feldman commitments, proofs of knowledge, nonce commitments,
  signature shares).
- Sealing uses `Noise_K_25519_ChaChaPoly_BLAKE2s` through `osst::sealed`, the
  same pattern ZF's `frost-client` uses for FROST DKG round 2. It binds the
  recipient (the responder's static key), the sender (the `ss` mix, which is
  what closes **D-2**), the ceremony (roster, session id and round number as
  the Noise prologue) and the dealer's Feldman commitment (a digest inside the
  sealed plaintext, so a sub-share and a commitment cannot be sourced
  separately).
- `open_subshare` runs the Feldman check itself and names the dealer on
  failure. A failure is a complaint, and **any complaint aborts the ceremony**.

### The signed roster

Each node has a static X25519 identity, generated at first start into
`<data-dir>/identity.key` with mode `0600` and derived from that seed with
`osst::sealed::x25519_secret_from_seed` — a KDF, so the decryption key is not
the identity seed itself. `--print-identity` prints the public half.

The roster is configuration: `--peer INDEX=URL=X25519_PUBKEY_HEX`, once per
member, identical on every node. Its fingerprint is SHA-256 over the sorted
`(index, pubkey, url)` triples, each field length-prefixed. `osst`'s own
`SealedRoster` carries only `(index, pubkey)` — a transport is out of scope for
the crate — so the URLs enter the Noise prologue transitively: the ceremony's
session id is `H(domain ‖ roster_hash ‖ epoch)`, and that session id is what
goes into the prologue with the roster and the round number. Two nodes that
disagree about any member's URL, key or index derive different session ids, and
their sealed packages simply do not open.

The same fingerprint is the `manifest_hash` of every signing context: the
roster *is* the group's membership manifest.

### Epoch-bound signing (N-1, R-1)

Signing is `osst::nested::inner_sign_v2_with_context`. The coordinator supplies
the whole outer round — every outer commitment, the group key, the nested
index, the session id, the bytes the outer package was built over — and each
node recomputes the binding factor, the challenge and the Lagrange coefficient
itself. The scalars the coordinator sends alongside are checked with
`InnerSigningParamsV2::from_coordinator_checked` and a disagreement is
`ChallengeMismatch`.

The bytes signed are
`SigningContext { epoch, manifest_hash, message }.encode()`, where the epoch
(the DKG generation counter) and the manifest hash come from **this node's own
key package**, never from the request. A node whose shares were generated in
epoch `e` builds context bytes for epoch `e`; a coordinator running a round for
`e+1` built its package over different bytes; the node refuses with
`MessageMismatch`. That is what retires an old share set after a
key-preserving reshare, which cannot otherwise be detected — the group public
key is deliberately unchanged.

This binding only works where the verifier is osst-aware. It does **not** apply
to a protocol-defined signature such as an Orchard `SpendAuthSig` over a
consensus-fixed sighash, where there is nowhere to put the epoch; retiring
shares there needs an on-chain rotation to a new group key.

### What is still missing

- The HTTP endpoints have no authentication of their own. The roster
  authenticates the DKG's secret round and the signing context, not the
  transport: anyone who can reach the port can start sessions and post public
  contributions. Keep the port on a private network.
- Resharing is not implemented, so the epoch only ever advances by re-running
  the DKG, which changes the group key.
- Nonce state is in memory. A node that restarts between round 1 and round 2
  loses its nonces, which is safe; a node that is restored from a snapshot
  could be made to reuse them, which is not. A durable spent-round store keyed
  by `(epoch, session_id, holder_index)` is `osst`'s open item A-3 and this
  crate's too.

## Design

The daemon follows a "your server as a function" decomposition (Marius
Eriksen): every protocol is built from reusable services, and HTTP handlers
stay thin — extract request, call service, serialize response.

### `accumulator.rs` — `ThresholdAccumulator`

Generic "collect contributions from peers until a threshold is met, then
aggregate". Sessions are keyed and contributions deduplicated by contributor
id. Both FROST rounds use the collected set itself as the aggregate: round 1's
product *is* the commitment set, and round 2's shares must be verified against
that set before they are summed, which needs more context than an aggregation
closure has.

### `identity.rs`, `roster.rs` — who the group is

The static X25519 identity and the signed roster described above.

### `broadcast.rs` — `PeerSet`

Two shapes, and the distinction is load-bearing: `broadcast` fans public data
out to every other member; `send_to` delivers one message to one member. DKG
round 2 uses `send_to` and nothing else.

### `dkg.rs` — `DkgCeremony`

Distributed interleaved key generation for the nested FROST position. Each node
acts as one dealer in `outer_t` independent Feldman VSS ceremonies, so the
inner group ends up holding Shamir shares of each coefficient of the outer
polynomial. Nobody learns the coefficients themselves.

1. **Round 1** — broadcast Feldman commitments and a Schnorr proof of knowledge
   of the constant term (Komlo–Goldberg SAC 2020 §5.1). The proof is verified
   by `osst::dkg::DkgState::submit_commitment` *before* the commitment is
   recorded, so a rogue-key setup has nowhere to start.
2. **Round 2** — one sealed package per recipient, delivered to that recipient
   only. Opening runs the Feldman check; a failure is a complaint naming the
   dealer, and aborts the ceremony.
3. **Round 3** — aggregate into this node's share of each outer coefficient,
   and write the key package.

The ceremony has no transport of its own: it produces messages and consumes
messages, and the delivery policy lives in the handlers. That is what lets the
whole protocol run in-process in a test, and it is why round 2 cannot
accidentally reach `broadcast`.

The participant set is the roster, in full. A member that does not commit
stalls the ceremony rather than being dropped from it — the previous
`close_round1()` behaviour, which locked in whoever committed in time, cannot
be reconciled with a roster fixed by configuration, and is deferred.

### `keypackage.rs` — persistence

`<data-dir>/key_package.json`, mode `0600`: the DKG generation, the roster
hash, this node's share of each outer coefficient, and the public verification
shares that make a bad round-2 signature share attributable. `format` is `2`
and only `2`; see the refusal note above.

### `signing.rs` — `SigningService`

Two-round nested FROST **v2**. Round 1 is `osst::nested::inner_commit` under
the session id; round 2 is `inner_sign_v2_with_context`. Shares are verified
individually against their commitments and public shares before being summed,
so a bad share names its holder instead of silently corrupting `z_nested`.

### `client.rs` — `NarsilClient`

The coordinator role: start round 1, wait for the threshold, build the outer
package, publish the whole outer round, wait for `z_nested`. It cannot make a
node sign anything the node has not independently derived.

## HTTP API

All endpoints are JSON.

| Method | Path | Purpose |
| --- | --- | --- |
| POST | `/sign/round1` | Start a signing session; returns this node's nonce commitments |
| POST | `/sign/commitment` | Peer submits its round-1 nonce commitment |
| POST | `/sign/status` | Poll progress; carries the nested commitment pair and `z_nested` |
| POST | `/sign/round2` | Publish the outer round; returns this node's share |
| POST | `/sign/share` | Peer submits its round-2 signature share |
| POST | `/dkg/init` | Begin a DKG ceremony for a generation |
| POST | `/dkg/round1` | Peer submits Feldman commitments and proof of knowledge |
| POST | `/dkg/round2` | Peer delivers this node's sealed sub-shares |
| POST | `/dkg/activate` | Re-install the persisted key package |
| GET | `/dkg/status` | Ceremony progress, including any complaint |
| GET | `/health` | Liveness, roster hash, identity, epoch |

## Running

Print each node's identity first, then give every node the same roster:

```
narsild --data-dir /var/lib/narsild --index 1 --print-identity
```

```
narsild \
  --bind 0.0.0.0:9200 \
  --data-dir /var/lib/narsild \
  --index 1 \
  --peer 1=http://val1:9200=<pubkey1> \
  --peer 2=http://val2:9200=<pubkey2> \
  --peer 3=http://val3:9200=<pubkey3> \
  --threshold 2 \
  --outer-threshold 1 \
  --nested-position 1
```

| Flag | Default | Meaning |
| --- | --- | --- |
| `--bind` | `0.0.0.0:9200` | Listen address |
| `--index` | – | This node's 1-indexed holder index; must be on the roster |
| `--data-dir` | `./narsild-data` | Identity and key package |
| `--peer` | – | `INDEX=URL=X25519_PUBKEY_HEX`, once per member |
| `--threshold` | `3` | Inner FROST threshold |
| `--outer-threshold` | `1` | Number of outer polynomial coefficients |
| `--nested-position` | `1` | The nested position's index in the outer signing set |
| `--print-identity` | – | Print the X25519 public key and exit |

Build and test from inside this directory so that the crate's own
`rust-toolchain.toml` applies:

```
cd crates/bin/narsild && cargo test && cargo clippy --all-targets -- -D warnings
```

## Intended use

`narsild` is the custody half of a shielded bridge between Penumbra and Zcash:
the validator set holds an Orchard escrow, and `narsild` produces the
threshold Orchard spend-authorization signatures needed to release funds. See
`docs/design/zcash-shielded-bridge.md`.
